# Resume Tailor

Resume Tailor is a single-user tool for tailoring one resume to one job description. You upload a resume PDF and
paste a job posting; the tool segments the PDF into bullets, scores every bullet against the job's extracted
requirements (worst first, with the matched terms that justify each score), asks one targeted question about
bullets that lack a measured result or that name nothing the job asks for, and rewrites those bullets using only
the facts you supply. It is aimed at one candidate working through one application at a time: there are no
accounts, no login, and no resume library in V1.

## Requirements

- Node.js 22 or newer (developed on v22.14.0).
- PostgreSQL running locally, with a database you can create (used via `DATABASE_URL`).
- Either a DeepSeek API key, or `LLM_PROVIDER=fake` to run the whole loop offline.

## Setup

```bash
npm install
createdb resume_tailor
cp .env.example .env
```

Fill in `.env` (see `.env.example`):

- `DATABASE_URL` — PostgreSQL connection string, e.g. `postgresql://USER@localhost:5432/resume_tailor?schema=public`.
  V1 expects a local database and the app refuses to start without it.
- `DEEPSEEK_API_KEY` — DeepSeek API key used for extraction and rewriting. Leave empty when using the fake provider.
- `LLM_PROVIDER` — optional. `deepseek` (default) or `fake`. `fake` runs the entire loop against a deterministic
  offline stand-in with no network call.
- `DEEPSEEK_MODEL` — optional. Defaults to `deepseek-chat`.

Apply the migrations (this also generates the Prisma client into `lib/generated/prisma`):

```bash
npm run db:migrate      # npx prisma migrate dev
```

## Running

```bash
npm run dev             # npx next dev, on http://localhost:3000
```

Open http://localhost:3000, upload a resume PDF, paste the JD, then work through the run detail page:
segmentation, scoring, questions, revisions, copy. The header shows which model is in use.

## Testing

Unit tests (`lib/**/*.test.ts`, Vitest):

```bash
npm test                # npx vitest run
```

End-to-end tests (Playwright, Chromium against `http://localhost:3000`):

```bash
npx playwright install chromium
npm run test:e2e        # npx playwright test
```

Playwright starts the app itself with `LLM_PROVIDER=fake`; stop a running `npm run dev` first, otherwise the suite
reuses that server and fails fast on its model guard instead of spending real credits.

`tests/smoke.spec.ts` uploads a generated PDF fixture, checks that every line is segmented (including lines with
no bullet glyph), scores all 8 bullets, and asserts they render worst-first with an overlap gap and a question on
the weakest one. `tests/segmentation.spec.ts` covers the editor that runs before scoring: edit, merge, reorder,
drop and add, it checks that only the surviving bullets get scored, and it checks that editing a scored bullet
marks that score stale until the run is scored again. `tests/focus.spec.ts` checks the triage groups (All /
Worth fixing / Off target / Already quantified) and that their counts account for every bullet. `tests/sections.spec.ts` clears a whole section in one confirmed action, including the
bullets that never got a heading. `tests/notes.spec.ts` drafts an answer from the candidate's notes, saves it,
rewrites from it, and checks that a bullet the notes do not cover is refused instead of invented. `tests/loop.spec.ts` drives the full loop
in the browser: answer a question, generate a revision, accept it and copy it out, reject and regenerate without
losing the earlier revision, edit a revision and keep the edited wording, and confirm re-scoring the same inputs
yields identical scores. Playwright runs the app with `LLM_PROVIDER=fake`, so the e2e suite needs no API key and
makes no network calls, and the fixture PDF is generated by `tests/fixtures/resume-pdf.mjs`, so no real resume is
committed to the repository.

## How it works

The pipeline has eight stages:

1. **Extract + segment** (`lib/pdf` → `lib/parse`) — PDF text → bullets, each with a section label and display order.
2. **JD Requirements** (`lib/model`) — LLM + Zod, once per JD: skills, tools, domain terms, seniority signals.
3. **Feature Extraction** (`lib/model`) — LLM + Zod, per bullet: skills, tools, action, whether it has a metric, scope.
4. **Score** (`lib/score`) — a pure function with no IO: weighted overlap with the JD requirements plus an evidence
   bonus, and the per-gap flags. **No model call happens inside `lib/score`** (ADR-0001).
5. **Question** (`lib/prompts`) — one question per gap type: overlap gap → "is this relevant to this JD, or should
   it be cut?"; evidence gap → "what was the measured result — latency, scale, throughput?".
6. **Extract Story Facts** (`lib/model`) — LLM + Zod over the candidate's Story: metric, scale, tool, timeframe.
7. **Revision** (`lib/generate`) — bullet + Story Facts + JD requirements → rewritten bullet under a strict schema;
   a value not present in the Story Facts must not appear in the revision.
8. **Decide** (API) — accepted / edited / rejected on one Revision, with a new row per regeneration.

Stage 2 runs once per JD rather than once per bullet: it is both the cost fix and the reason scoring is
reproducible.

Module map:

- `lib/parse` — PDF text, bullet segmentation, normalization.
- `lib/pdf` — PDF → plain text via `unpdf`; the only code that knows PDF internals.
- `lib/score` — pure scoring and input hashing; imports nothing that does IO.
- `lib/model` — the whole LLM surface (JD requirements, bullet features, story facts, answer draft, revision) plus the fake adapter and the model label.
- `lib/generate` — revision generation, including the check that rejects invented numbers.
- `lib/prompts` — prompt text and versions, shared by the extraction and generation calls.
- `lib/run` — the run orchestration: create, segment, evaluate, story, revision, decision.
- `lib/schemas`, `lib/diff`, `lib/api`, `lib/client`, `lib/db`, `lib/owner`, `lib/errors` — Zod schemas,
  word-level diff, HTTP helpers, Prisma client, and the single local owner.
- `app/api/*` — thin route handlers: create run, edit·merge·delete bullets, evaluate, submit story, generate
  revision, decide revision.
- `components/*` — `UploadForm` (start a run), `RunNotes` (the candidate's notes a draft is built from),
  `SegmentationEditor` (fix, merge, reorder or clear bullets before scoring), `BulletWorkbench` (triage groups,
  questions, diff, decisions, copy).
- `app/page.tsx` — run list; `app/runs/[id]/page.tsx` — run detail.

## Data model

Tables in `prisma/schema.prisma`:

- `users` — the single local owner (created lazily, no login in V1).
- `resumes` — an uploaded resume and its extracted raw text, scoped to a run's input.
- `job_descriptions` — the pasted JD text; `jd_requirements` — the terms extracted once per JD.
- `tailoring_runs` — one resume paired with one JD; stores only its identity and inputs.
- `resume_bullets` — the segmented bullets, editable before scoring.
- `bullet_evaluations` — per-bullet features, the text it scored, match score, matched/missing terms, gap flags,
  question, scoring version, inputs hash.
- `bullet_stories` — the candidate's raw answer and the Story Facts extracted from it.
- `bullet_revisions` — each generated rewrite, its claims, decision, and model.

A tailoring run's status is derived rather than stored: progress (scored, answered, revised, decided) is computed
from its child rows on read (ADR-0003). Every table carries `owner_id` (ADR-0002).

## Decisions and vocabulary

- [CONTEXT.md](CONTEXT.md) — the glossary: canonical names for Bullet, Match Score, Overlap Gap, Evidence Gap,
  Story, Story Fact, Revision, Decision, plus the terms reserved for V2.
- [`docs/adr/0001`](./docs/adr/0001-match-scores-computed-in-code.md) — Match Scores come from a pure function,
  never from the model.
- [`docs/adr/0002`](./docs/adr/0002-single-tenant-tenancy-shaped.md) — V1 has one local user and no auth, but
  every table is tenancy-shaped via `owner_id`.
- [`docs/adr/0003`](./docs/adr/0003-run-status-is-derived.md) — a run's status is derived from its child rows,
  never stored.
- [`docs/adr/0004`](./docs/adr/0004-retire-typesafe-jev-terminology.md) — "TypeSafe Jev" is retired; Feature
  Extraction and JD Requirements are the names.

## Deliberate V1 limits

The following are cut to V2 by design (see "Cut to V2" in [docs/v1-spec.md](docs/v1-spec.md)), not missing work:

- Auth and the SaaS template; Framer Motion; TanStack Table.
- DOCX/PDF generation (output is copied as a markdown block); voice storytelling; mock interview prep; aggregate
  skill-gap analysis.
- Master Resume and Resume Variants; Candidate Preferences; Story Library imports (e.g. seeding from an existing
  career narrative document).
